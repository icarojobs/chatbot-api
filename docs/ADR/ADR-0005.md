# ADR-0005 — Hospedagem em Google Cloud Run + Neon

- **Status:** Substituído pelo [ADR-0010](ADR-0010.md) (a conta de faturamento do Google Cloud foi bloqueada)
- **Data:** 27/10/2026
- **Contexto de decisão:** [RFC-0002](../RFC/RFC-0002.md), [DECISAO_TECNICA](../hospedagem/DECISAO_TECNICA.md), Fase 7 do [plano](../planejamento/PLANO_DE_DESENVOLVIMENTO.md)

## Contexto

A API precisa ficar no ar sem quedas durante a avaliação (data desconhecida), suportar SSE, uploads de PDFs de 16 MB+ e persistir documentos e vetores.

## Decisões

1. **Cloud Run** para a API (container, SSE, 32 MiB por requisição, franquia gratuita) com `min-instances=1` e CPU sempre alocada; Render descartado por suspensão e disco efêmero; Vercel descartada pelo limite de 4,5 MB por requisição e duração das funções.
2. **Neon** (Postgres gerenciado com pgvector, plano gratuito) como banco; conexão direta (sem pooler) por causa dos prepared statements automáticos do psycopg 3.
3. **Segredos no Secret Manager**, injetados como variáveis de ambiente; nada sensível na imagem nem no repositório.
4. **Deploy por script idempotente** (`make deploy`) em vez de CI/CD automático: o deploy depende de credenciais do dono da conta e acontece poucas vezes no escopo do desafio.
5. **Migrations no start do container**, serializadas por advisory lock (ADR-0003).
6. **Ingestão de produção** pela CLI apontando para o Neon (`make ingest-prod`) ou pela API de upload.

## Consequências

- Custo baixo, mas não zero, pela instância mínima com CPU sempre alocada (alternativa documentada: `MIN_INSTANCES=0`).
- Sem pipeline de deploy contínuo: cada release exige `make deploy` local.
- Cold start do Neon após inatividade (~1 s na primeira consulta).
