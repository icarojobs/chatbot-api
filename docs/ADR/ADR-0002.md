# ADR-0002 — Provedores compatíveis com OpenAI e ambientes dev/prod

- **Status:** Aceito
- **Data:** 27/10/2026
- **Contexto de decisão:** [RFC-0002](../RFC/RFC-0002.md), Fase 2 do [plano](../planejamento/PLANO_DE_DESENVOLVIMENTO.md)

## Contexto

O README exige trocar de modelo sem reescrever a integração. As regras do projeto exigem Ollama em `development` e o provedor real apenas em `production`.

## Decisões

1. **Um único adaptador** (`OpenAICompatibleProvider`) sobre o SDK `openai`. O Ollama expõe `/v1` compatível com a OpenAI, então dev e prod mudam apenas `base_url`, chave e modelos — sem `if` por ambiente no código de negócio.
2. **Contratos próprios** (`ChatModelProvider`, `EmbeddingProvider`) isolam o SDK: o RAG (Fases 3–6) depende só dos Protocols.
3. **`ProviderProfile`** escolhido pelo `API_ENV` funciona como allowlist: só modelos configurados são aceitos (`model_not_found` caso contrário), e o primeiro da lista é o padrão. `API_ENV=production` sem as variáveis do provedor falha no startup.
4. **Erros do provedor traduzidos** para `ApiError` com mensagens públicas fixas (timeout → 504, indisponível → 502, rate limit do provedor → 503, demais → 502). Detalhes ficam só no log, sem conteúdo do prompt.
5. **Embeddings em lotes de 64**, ordenados pelo `index` retornado e validados (quantidade e dimensão únicas) — vetores inválidos nunca chegam ao índice.
6. Cliente HTTP criado **uma vez por processo** no lifespan e fechado no shutdown.

## Validação real (smoke tests de 27/10/2026)

| Verificação | Resultado |
|---|---|
| `cohere/embed-v4.0` | 1536 dimensões; `encoding_format="float"` aceito |
| `azure/gpt-6-luna` streaming | OK, TTFT ~1,6 s |
| `azure/gpt-5-mini` streaming com `max_completion_tokens=200` | **resposta vazia**: o modelo de raciocínio consumiu o limite pensando |
| `azure/gpt-5-mini` com limite maior | OK (64 tokens de raciocínio para responder "ok") |
| Ollama `bge-m3:567m` | 1024 dimensões |
| Ollama `qwen3:4b` (com raciocínio), CPU | TTFT de **253 s** — inviável |
| Ollama `qwen3:4b-instruct-2507-q4_K_M`, CPU | TTFT 0,1 s (modelo carregado), ~2,6 s por resposta curta |

## Consequências

- **Troca do modelo de dev:** `qwen3:4b` foi substituído pela variante **instruct-2507** (mesma família, sem modo de raciocínio). `reasoning_effort="none"` fazia o raciocínio vazar para o conteúdo e `think: false` foi ignorado pelo endpoint compatível.
- **`LLM_MAX_OUTPUT_TOKENS` padrão 1500** e uso de `max_completion_tokens` (não `max_tokens`), para que modelos de raciocínio tenham folga.
- Dimensões diferentes entre dev (1024) e prod (1536): o armazenamento vetorial (Fase 3) separa vetores por modelo de embedding.
- Tags dos modelos do Ollama fixadas (`bge-m3:567m` em vez de `latest`).
