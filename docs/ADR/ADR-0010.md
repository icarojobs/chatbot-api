# ADR-0010 — Hospedagem na Vercel + Neon

- **Status:** Aceito (substitui o [ADR-0005](ADR-0005.md))
- **Data:** 28/10/2026
- **Contexto de decisão:** [RFC-0004](../RFC/RFC-0004.md)

## Contexto

O ADR-0005 escolheu o Cloud Run e descartou a Vercel pelo limite de 4,5 MB por requisição e pela duração das funções. A conta de faturamento do Google Cloud foi bloqueada, e sem faturamento ativo o Cloud Run não funciona. Os dois motivos do descarte foram reavaliados:

- **4,5 MB por requisição:** o upload em partes (Fase 4) já envia partes de 4 MiB, então PDFs grandes continuam funcionando. Só o upload direto precisa de um limite menor.
- **Duração:** no plano Hobby, com Fluid compute, cada invocação dura até **300 s**. É suficiente para respostas em streaming e para gerar os embeddings de um PDF depois do `complete`.

## Decisão

1. **API na Vercel (plano Hobby), runtime Python nativo**, região `gru1` (São Paulo), a mesma do Neon (`aws-sa-east-1`).
   - Entrada: `src/chatbot_api/asgi.py` (`app = create_app()`), declarada em `[tool.vercel] entrypoint` no `pyproject.toml`.
   - Dependências instaladas a partir do `uv.lock`, com Python 3.14.
   - `vercel.json` define a região, `maxDuration` de 300 s e exclui do pacote testes, docs, avaliação e scripts.
2. **Migrations no build** (`[tool.vercel.scripts] build`), com o advisory lock do ADR-0003. Se uma migration falhar, o deploy falha e a versão anterior continua no ar.
3. **Deploy contínuo pela integração Git da Vercel, só na `main`** (`git.deploymentEnabled`: `"*": false`, `"main": true`). Os previews ficam desligados para não tocar no banco de produção.
4. **Variáveis de ambiente na Vercel**, gravadas por `make deploy-env` a partir do `.env.production`:
   - credenciais (`DATABASE_URL`, chave do provedor e tokens) como **sensitive**, que não podem ser lidas depois;
   - valores fixos da plataforma: `API_ENV=production`, `TRUSTED_PROXY_HOPS=1` e `DIRECT_UPLOAD_MAX_BYTES=4194304`.
5. **Neon com conexão direta** (sem pooler), como no ADR-0005, por causa dos prepared statements automáticos do psycopg 3. Cada instância mantém o pool atual (5 + 5 conexões).
6. **Carga inicial** copiando a base já ingerida localmente (`make copy-db-neon`: migrations e depois `pg_dump --data-only` de `documents`, `chunks` e `chunk_embeddings`), sem gerar os embeddings de novo. O script só roda com o Neon vazio.

## Consequências

- **Custo zero** dentro dos limites do Hobby, que é para uso não comercial e serve para a avaliação.
- **Cold start:** as instâncias escalam até zero quando não há uso. A primeira requisição depois de um tempo parado inclui a subida do Python e, se o Neon estiver suspenso (após 5 min), o despertar do banco.
- **Rate limit por instância:** o limite fica em memória (ADR-0001). Com várias instâncias, o limite efetivo se multiplica; para o escopo atual, isso é aceitável.
- **IP do cliente:** a Vercel sobrescreve o `X-Forwarded-For` com o IP real, então `TRUSTED_PROXY_HOPS=1` não pode ser forjado pelo cliente.
- **Embedding em background:** o `BackgroundTasks` roda dentro da mesma invocação e cabe nos 300 s. Para bases muito maiores, a evolução seria uma fila (Vercel Queues).
- **Reset da base habilitado em produção** (`DOCUMENTS_RESET_ENABLED=true`), para que quem avalia a API possa testar todos os endpoints. Ele continua exigindo o token admin e `confirm=true`; a base é restaurada com `make copy-db-neon`, que só copia para um banco vazio.
- **Upload direto limitado a 4 MiB em produção.** Acima disso, a resposta é `413 file_too_large`, que orienta a usar o upload em partes.
- O `Dockerfile` continua sendo usado no ambiente local (`make up`, `make up-prod`). O script do Cloud Run foi removido; se o faturamento voltar, ele pode ser recuperado no histórico do Git.
