# RFC-0002 — Decisões de base para o desenvolvimento

- **Status:** Aprovada
- **Data:** 27/10/2026
- **Autor:** icarojobs
- **Resultado:** [Plano de desenvolvimento](../planejamento/PLANO_DE_DESENVOLVIMENTO.md)

## Contexto

O README, o `CLAUDE.md` e o rascunho de arquitetura (`playground/rag-chatbot-architecture.md`, não versionado) divergiam em pontos que mudam a arquitetura. Esta RFC fixa as decisões antes de qualquer código.

## Decisões

| # | Questão | Opções | Decisão |
|---|---|---|---|
| 1 | Ingestão de documentos | API autenticada + CLI · Só CLI · Só API | **API autenticada + CLI**, compartilhando o mesmo pipeline |
| 2 | Contrato do chat | OpenAI-compatible · OpenAI + SSE próprio · Só SSE próprio | **OpenAI-compatible** (`/v1/chat/completions`, `/v1/models`), fontes em campo extra `sources` |
| 3 | Persistência | PostgreSQL + pgvector · Índice NumPy + Cloud Storage · Índice na imagem | **PostgreSQL + pgvector** |
| 4 | Versão do Python | Testar 3.15 com fallback · 3.15 obrigatório · 3.14 | **Python 3.14.x** |
| 5 | Modelos em development (Ollama) | qwen3:4b + bge-m3 · llama3.2:3b + nomic-embed-text · gemma3:4b + embeddinggemma | **qwen3:4b + bge-m3**, Ollama via docker compose com GPU |
| 6 | Hospedagem | Cloud Run + Neon · Cloud Run + Supabase · Cloud Run + Cloud SQL | **Cloud Run + Neon** |
| 7 | CI de qualidade | Só na fase final · Desde a fase 1 · Nenhuma | **CI leve desde a fase 1** (ruff + mypy + pytest); Security segue desativado até a fase final |
| 8 | Autenticação | Bearer token estático · Sem auth · JWT com usuários | **Bearer token estático** (token de chat e token admin para upload) |

## Justificativas

1. **Ingestão:** o README exige carga via API; a CLI reaproveita o mesmo pipeline para a carga inicial das apostilas, sem duplicar código.
2. **Contrato:** o README exige formato idêntico ao da OpenAI; com ele, qualquer SDK/cliente existente funciona trocando só `base_url` e `api_key`. Clientes OpenAI ignoram o campo extra `sources`.
3. **Persistência:** o Cloud Run tem disco efêmero e pode ter várias instâncias; um índice local perderia uploads a cada restart. O pgvector dá durabilidade, concorrência correta e filtros por metadados.
4. **Python 3.14:** o 3.15 acabou de sair e libs com extensão nativa podem não ter wheels; o 3.14 elimina esse risco num prazo curto. README e `CLAUDE.md` foram atualizados.
5. **Ollama:** `qwen3:4b` (~2,6 GB) cabe nos 4 GB da GTX 1650 SUPER e responde bem em pt-br; `bge-m3` é multilíngue. Como o Ollama expõe API compatível com a OpenAI, dev e prod usam o mesmo adaptador.
6. **Hospedagem:** segue `docs/hospedagem/DECISAO_TECNICA.md` (Cloud Run); Neon é Postgres gerenciado com pgvector no plano free.
7. **CI:** ~1 min por PR garante o gate de 95% de cobertura sem atrasar o desenvolvimento; os scanners pesados voltam na entrega.
8. **Auth:** SDKs OpenAI enviam a `api_key` como `Authorization: Bearer`, então o token estático funciona sem adaptação no cliente e protege os créditos do provedor.

## Consequências

- Embeddings de dev e prod não são comparáveis: os vetores ficam separados por modelo de embedding, e a qualidade do retrieval só é medida de fato em produção.
- `min-instances=1` com CPU sempre alocada no Cloud Run pode gerar custo baixo fora do free tier.
- ADRs previstos: ADR-0001 (stack/Python 3.14), ADR-0002 (provedores dev/prod), ADR-0003 (pgvector), ADR-0004 (Cloud Run + Neon), criados nas fases correspondentes.
