# RFC-0001 — Pipeline de segurança no GitHub Actions

- **Status:** Aprovada
- **Data:** 27/10/2026
- **Autor:** icarojobs

## Contexto

Todo PR e todo código que chega à `main` precisa ser barrado caso introduza vulnerabilidades (SAST), SQL injection, CVEs em dependências ou segredos vazados — sem tornar o pipeline lento.

Ferramentas avaliadas: CodeQL, Semgrep, Bandit, pip-audit, Gitleaks, Trivy e OWASP ZAP.

## Decisões

| # | Questão | Opções | Decisão |
|---|---|---|---|
| 1 | Ferramentas | Enxuto sem redundância · Todas as 7 · Enxuto + Bandit | **Enxuto sem redundância**: CodeQL + Semgrep + pip-audit + Gitleaks + Trivy |
| 2 | OWASP ZAP | Workflow separado depois · Criar desabilitado · Rodar em todo PR | **Workflow separado depois**, quando existir API para escanear |
| 3 | O que bloqueia o merge | HIGH + CRITICAL · Tudo · Apenas reportar | **HIGH + CRITICAL** |
| 4 | Gatilhos | PR + push main + semanal · Apenas PR + push main | **PR + push main + cron semanal** |

### Justificativas

- **Bandit fora:** as regras dele já são cobertas pelo CodeQL (`security-extended`) e pelo Semgrep. Quando o projeto tiver o Ruff, as regras `S` (flake8-bandit) cobrem o restante em milissegundos.
- **OWASP ZAP fora:** DAST exige a API rodando e leva de 5 a 15 minutos. Hoje não há código para escanear. Entrará como workflow agendado/manual, sem bloquear PRs.
- **Rulesets do Semgrep:** `p/default` + `p/python` + `p/owasp-top-ten`. Em teste local, `p/sql-injection` e `p/security-audit` **não** detectaram `cursor.execute("... '%s'" % name)`; o `p/default` detectou com nível `error`.
- **Cron semanal:** detecta CVEs publicadas depois do último PR em dependências que não mudaram.

## Desenho

`.github/workflows/security.yml` com 5 jobs paralelos (tempo total ≈ o job mais lento, ~3–5 min):

| Job | Cobertura | Critério de bloqueio |
|---|---|---|
| CodeQL | SAST Python (fluxo de dados, injection) | `security-severity` ≥ 7.0 |
| Semgrep | SAST, SQL injection, OWASP Top 10, Dockerfile, workflows | regra com nível `error` |
| pip-audit | CVEs nas dependências do `uv.lock` | qualquer vulnerabilidade com versão corrigida |
| Gitleaks | segredos em todo o histórico git | qualquer achado |
| Trivy | CVEs (lockfiles) e misconfig (Dockerfile/IaC) | `security-severity` ≥ 7.0 |

- Todos os relatórios SARIF vão para a aba **Security → Code scanning**, inclusive achados MEDIUM/LOW, que não bloqueiam.
- O gate é centralizado em `.github/scripts/sarif_gate.sh` (mapeamento do GitHub: ≥ 7.0 = HIGH, ≥ 9.0 = CRITICAL). O pip-audit, que não informa severidade, usa `.github/scripts/pip_audit_gate.sh`.
- CodeQL e pip-audit são pulados automaticamente enquanto não existirem arquivos `.py` / `uv.lock`.
- `concurrency` cancela execuções antigas do mesmo PR.
- Em PRs vindos de forks o token não tem `security-events: write`: os gates continuam rodando, só o upload do SARIF é pulado.

## Segurança da cadeia de suprimentos

- Actions fixadas por **SHA de commit** e imagens Docker por **digest** (nunca `latest`), mitigando sequestro de tags.
- `permissions: contents: read` por padrão; `security-events: write` só nos jobs que enviam SARIF; `persist-credentials: false` no checkout.
- O Dependabot atualiza semanalmente os SHAs das actions. As imagens Docker (Semgrep, Gitleaks e Trivy) precisam ser atualizadas manualmente (versão + digest) nas variáveis `*_IMAGE` do workflow.

## Próximos passos

- Ativar uma **branch protection rule** na `main` exigindo os 5 checks.
- Adicionar o ecossistema `uv` ao Dependabot quando existir o `uv.lock`.
- Workflow do OWASP ZAP (API scan) quando a API e o Dockerfile existirem.
