# RFC-0003 — CORS para chamadas a partir do navegador

- **Status:** Aprovada
- **Data:** 27/10/2026
- **Autor:** icarojobs

## Contexto

Para validar o streaming (`stream=true`) e a resposta completa (`stream=false`) em localhost e em produção, foi criada uma página HTML simples (`playground/test-stream.html`, não versionada) que chama `POST /v1/chat/completions` via `fetch`. Sem CORS, o navegador bloqueia a chamada (inclusive o preflight `OPTIONS` disparado pelo header `Authorization`).

## Decisões

| # | Questão | Opções | Decisão |
|---|---|---|---|
| 1 | Como liberar as origens | Variável com padrão `*` · `*` fixo no código | **Variável `CORS_ALLOWED_ORIGINS`** (lista separada por vírgula), padrão `*` em dev e prod |
| 2 | Posição do middleware | Mais externo · Interno ao rate limit | **Mais externo**: erros (`401`, `429`) também levam os headers CORS |
| 3 | Isolamento da mudança | Worktree a partir da `main` · Branch em andamento | **Worktree/branch própria** (`feat/cors`), sem misturar com outro trabalho |

## Justificativas

- **`*` é seguro aqui:** a autenticação é Bearer no header e a API não usa cookies; `allow_credentials` fica desligado. Uma página maliciosa não consegue "pegar carona" em credenciais do navegador.
- **`file://`:** a página aberta direto do disco envia `Origin: null`, coberto pelo `*`.
- **Middleware externo:** se o CORS ficasse dentro do rate limit, o `429` sairia sem headers CORS e o navegador mostraria só "CORS error". O preflight é respondido pelo próprio middleware de CORS, antes da rota; as requisições reais continuam passando pelo rate limit.
- **Middleware ASGI puro:** o `CORSMiddleware` do Starlette não bufferiza o corpo, então o SSE continua chegando aos poucos (ADR-0001).
